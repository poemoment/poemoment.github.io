过去一个月我在同时推进两个项目：一个本地个人助理（personal-assistant），一个给各种 agent 宿主装的长期记忆服务器（dsh-memory）。一个是 FastAPI 模块化单体加 Tauri 桌面壳，一个是只依赖两个包的 MCP stdio 服务器——形态完全不同，但长着长着，它们共用出了同一套工程判断。这篇文章把这套判断记下来。

核心只有一句话：**模型只做非确定性事务，其余一切还给程序。**

## 确定性与非确定性，严格分离

时间、状态、去重、提醒、幂等——这些事有唯一正确答案，由普通代码负责。理解、提取、建议——这些事没有唯一正确答案，才轮到模型。

个人助理里有一个 `TaskWorkflowStatus` 状态机：任务从待办到进行中到完成，非法跳转直接拒绝。这个判断没有任何"智能"成分，也不该有。同样，提醒策略是"作业提前 1 天、3 小时、30 分钟"这样的死规则；如果让模型决定什么时候提醒，它早晚会在某个凌晨三点给你发一条"看起来该起了"。

## LLM 提议，程序决定

模型产出的任何东西——一条记忆、一次任务拆解、一封邮件草稿——都先落成"候选"，经过硬校验，再由人确认入库。

dsh-memory 的写入门卫是最极端的例子：11 类条目的白名单、shared 域的证据强制（没有原文短引的观点会被真实拒绝）、三层去重、纠错必须指向被修正的旧条目。模型不能自选权限——scope 和 role 只来自启动时的环境变量，参数里没有这两个字段。

有一次测试让我印象很深：验证流程里我随口让模型"记住一个口令"，它调用了记忆工具，但**拒绝**把这个口令升级成"用户偏好"——因为证据等级不够。这就是门卫存在的意义：不是不信任某个模型，而是不信任"模型一定不会被自己说服"这件事。

## 诚实降级

失败要显式返回，不静默吞掉，不假装成功。

FTS5 全文检索不可用时，系统返回 `degraded` 标记而不是悄悄退化成无检索；邮件发送结果是 `unknown` 时，走人工核对而不是自动重试——因为自动重试可能把同一封信发两遍，而"显示我不知道"永远不会伤害任何人。

## 可审计、可回滚

每条记忆带证据链：原文短引、来源、日期。纠错不覆盖旧记录，而是把旧记录转成 superseded，新记录指向它——错误也是历史的一部分。关键动作落审计事件，出事能回放。

这四条听起来朴素，但它们是少数我在两个项目里都从来没有后悔过的决定。反过来，每一次"这里让模型顺手处理一下"的偷懒，后来都变成了 bug 或者更难维护的边界。

如果你也在做 agent 类的东西，我的建议是：先画一条线，线上是确定性代码的地盘，线下才是模型的。线画得越早，系统越长寿。
